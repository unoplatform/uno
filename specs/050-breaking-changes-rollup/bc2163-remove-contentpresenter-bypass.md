# #2163 — Remove the `ContentPresenter` bypass

**Epic:** [#8339](https://github.com/unoplatform/uno/issues/8339) · **Danger:** 2/5 · **Effort:** M

## TL;DR

`ContentControl` carried a Uno-only shortcut — `IsContentPresenterBypassEnabled` — that skipped the
`ContentPresenter` and parented `Content` (or the materialized `ContentTemplate`) directly, whenever the
control had no `Template` *and* its default style declared no `Template` setter. It is removed, along
with the memoized default-template lookup that drove it.

## Correction to the issue framing: the bypass was already inert

The issue reads as a behavioural fix ("we are using `ContentPresenter` bypass, which misaligns our
behavior against WinUI"). Measured against the code, the bypass had **already stopped engaging** on every
target Uno.UI ships. Recording this so the next reader does not go looking for a rendering change.

The default `ContentControl` template in `Generic.xaml` is gated on a conditional-XAML prefix, and at the
time of writing that prefix was spelled `netstdref:` — which reads like "reference/stub build only". It
never meant that: `_IsNetStdRef` was true whenever `UnoRuntimeIdentifier` was `Skia` or `WebAssembly`, or
the target framework was plain `netX.0`. `Uno.UI.csproj` sets `UnoRuntimeIdentifier=Skia` and targets Skia
TFMs only — there is no native Android/iOS `Uno.UI` build any more — so the setter was always included,
`HasDefaultTemplate(typeof(ContentControl))` was always `true`, and `IsContentPresenterBypassEnabled` was
always `false` for a bare `ContentControl`.

The `netstdref` / `not_netstdref` prefixes have since been retired from the whole repo; the setter now
carries `not_winappsdk:`, which says what it means — emit this template on every head Uno draws, and leave
it out of the WinAppSDK head, where WinUI supplies it. For `Uno.UI` that is unconditionally true, so the
conclusion is unchanged; only the misleading spelling is gone. **This PR therefore makes no change to
`Generic.xaml`.**

An independent record of the same fact already lived in the test suite, in
`Uno.UI.UnitTests/Windows_UI_Xaml/Given_FrameworkTemplate.cs`:

> *"Real Skia applies the default ContentControl ControlTemplate (a ContentPresenter), so the materialized
> ContentTemplate root lives on the inner ContentPresenter, not on ContentControl.ContentTemplateRoot
> (which stays null when a template is present)."*

The bypass was leftover native-Android/iOS machinery: its own doc comment cited the Android 4.4 32 KB
stack limit, fixed by ART and irrelevant since the native rendering layer was dropped.

## What changed

1. **`ContentControl`** loses `IsContentPresenterBypassEnabled`, the `HasDefaultTemplate` /
   `CreateHasDefaultTemplateMemo` / `ClearHasDefaultTemplateCache` memo, `ClearContentPresenterBypass`,
   `SetUpdateTemplate`, `UpdateContentTemplateRoot`, `SyncDataContext`, the content-DataContext override
   plumbing, the `ImplicitTextBlock` placeholder path, and the `OnLoaded` / `OnVisibilityChanged` /
   `OnDataContextChanged` / `MeasureOverride` overrides that existed only to drive it. The
   `Content` / `ContentTemplate` / `ContentTemplateSelector` / `ContentTransitions` properties and the
   `protected virtual On*Changed` overridables are unchanged.
2. **`Generic.xaml`** — unchanged. The prefix cleanup that retired `netstdref:` in favour of
   `not_winappsdk:` landed on the base branch independently.
3. **`Application.Alc.cs`** loses the `ClearHasDefaultTemplateCache` teardown step (and
   `Uno.UI.UnitTests/ContentControlTests/Given_ContentControl_DefaultTemplateMemo.cs`, the test guarding
   it). The memo was a `Type`-keyed static that pinned collectible ALCs; deleting it removes both the leak
   and its workaround.
4. **`FrameworkElement.ApplyTemplate`** — the guard collapses to `!HasTemplateChild()`. The
   `(this as ContentControl)?.Content == GetFirstChild()` clause and the `ClearContentPresenterBypass()`
   escape hatch existed only because the bypass could park `Content` as a direct child.
5. **`ButtonBase`** loses `OnContentTemplateRootSet() => RegisterEvents()` and the `partial void
   RegisterEvents()` it called. The hook only fired under the bypass, and the partial had no remaining
   implementation once the native Android/iOS partials were dropped.
6. **`ContentControl.ContentTemplateRoot`** becomes get-only (public surface) and is now reported by the
   `ContentPresenter` of the applied template. See below.

## `ContentTemplateRoot`: one accessor, on `ContentControl`

`ContentTemplateRoot` is genuine WinUI API on **`ContentControl`** and does not exist on WinUI's
`ContentPresenter`. Evidence, all local:

- `Generated/3.0.0.0/Microsoft.UI.Xaml.Controls/ContentControl.cs` carries
  `// Skipping already declared property ContentTemplateRoot` and
  `// Forced skipping of method …ContentControl.ContentTemplateRoot.get`. These stubs are generated by
  walking the WinAppSDK reference metadata; a member absent from that metadata produces no line at all.
- Only a `.get` is listed — WinUI's property is read-only. Uno's `protected set` was the divergence, so
  removing it from the public surface is parity.
- `Uno.WinAppSDKSyncGenerator/Helpers/SymbolMatchingHelpers.cs` carved `ContentTemplateRoot` out of the
  property type-matching check *because* Uno typed it as the per-platform native view.
- The generated `ContentPresenter` stub contains no `ContentTemplateRoot` line whatsoever. Its Uno-only
  public property had already been reduced to `internal` under BC36.

Because the bypass never assigned it in shipping builds, `ContentControl.ContentTemplateRoot` returned
`null` for every control. It is now set by the templated `ContentPresenter`, which mirrors WinUI's
`CContentPresenter` writing `ContentControl::m_tpContentTemplateRoot`. Three MUX ports read it and
degraded silently on `null`: `HyperlinkButton` (underline of the implicit text), `SelectorItem`
(automation-name fallback) and `ItemsRepeaterScrollHost` (`TransformToVisual` against the scroll
viewer's content root).

Known simplification: when a template hosts several `ContentPresenter`s under the same templated parent
(ContentDialog's Title/Icon, CommandBar), the reporting presenter is selected by comparing the `Content`
**dependency-property values** of presenter and parent. The DP values must be compared rather than the CLR
properties, because `ContentControl.Content`'s getter returns `DataContext` when the DP is unset and
`ContentTemplate` is set. If both sides are null the last presenter to materialize wins.

## Behaviour deltas

1. A `ContentControl` subclass that sets its own `DefaultStyleKey` and provides **no** `Template` in its
   default style no longer renders `Content`. This is the only app-visible break, and it restores WinUI
   behaviour. In-framework, only the unused `DatePickerSelector` / `TimePickerSelector` are in that shape.
2. `ContentControl.ContentTemplateRoot` goes from always-`null` to populated, activating the three MUX
   paths above.

Everything else — padding, content alignment, the presenter layer, `templatedParent` on `ContentTemplate`
roots — is unchanged, because it was already the shipping behaviour.

## Not fixed here

- The default style sets `HorizontalContentAlignment="Left"` / `VerticalContentAlignment="Top"` while
  BC45 moved `Control`'s DP defaults to `Center`/`Center`. Both are live today and they disagree once the
  style applies. Needs a native-WinUI measurement and its own item; bundling a real visual change into a
  dead-code removal would be wrong.
- `ItemsControl.GetGroupHeaderContainer` still returns a `ContentControl` where WinUI returns a
  `ContentPresenter`. Observable through `ItemContainerStyle` and `ContainerFromItem` casts — its own item.
- `SymbolMatchingHelpers.ArePropertiesMatching` has its `IsReadOnly`/`IsWriteOnly` checks commented out.
  That is why Uno's extra `protected set` on a read-only WinUI property was never flagged; the sync
  generator structurally cannot catch accessor divergence.
