### Step 4 — `fix(avp): Restore WinUI play-duration and scope the hit-test change`

Four corrections on top of B's port.

**(4a) `m_playDuration` — compute in the ctor, per `AnimatedVisualPlayer.cpp:12-28`.**

I read the C++ to settle this rather than accept either branch. `cpp:22-27`:

```cpp
// Save the play duration as time.
// If toProgress is less than fromProgress the animation will wrap around, ...
const auto durationAsProgress = fromProgress > toProgress ? ((1 - fromProgress) + toProgress) : (toProgress - fromProgress);
// NOTE: this relies on the Duration() being set on the owner.
m_playDuration = std::chrono::duration_cast<winrt::TimeSpan>(m_owner->Duration() * durationAsProgress);
```

A computes here (correct, matches WinUI); B computes a local in `Start()`.

`UpdateContent` (read at `cpp:1055-1077`) sets `Duration(animatedVisual.Duration())` **before** `IsAnimatedVisualLoaded(true)` and before `if (m_nowPlaying) m_nowPlaying->Start(); else if (AutoPlay()) ... PlayAsync(...)`. So the **AutoPlay path always sees a correct Duration in the ctor**, and the `m_nowPlaying` branch only fires on reentrance from a DP handler that ran *after* `Duration()` was set. WinUI's ctor computation is therefore correct in every case WinUI actually exercises.

The one case it is wrong is **user code calling `PlayAsync` before the source loads** — `cpp:708-713` skips `Start()` when `!IsAnimatedVisualLoaded()`, so the play was constructed with `Duration == 0`, and `Start()` then takes the `< 20ms` fast path (`cpp:44-51`, read) and self-completes without animating. That is genuine WinUI behaviour, and it is **rare on Windows** (LottieGen sources are synchronous) but **the normal case on Uno**, because B's own Lottie design loads JSON asynchronously.

**Decision:** restore A's ctor computation as the primary, and recompute in `Start()` **only when the ctor-time value was zero**, marked as a deliberate divergence:

```csharp
// TODO Uno: WinUI computes m_playDuration once in the AnimationPlay ctor (cpp:12-28) and relies on
// Duration() already being set. Uno's animated-visual sources load asynchronously, so a PlayAsync()
// issued before the source resolves would otherwise carry a zero duration and self-complete via the
// <20ms fast path (cpp:44-51). Recompute only in that case; every path WinUI exercises is unchanged.
```

Keep B's `HasStarted()` and `UnloadContent(bool preserveUnstartedPlay)` (they cover the same async-source gap; `cpp:930` calls `Stop()` unconditionally) and mark both with `// TODO Uno:` for the same reason.

**(4b) Scope the hit-test change to the player.** B replaces `internal override bool IsViewHit() => false;` with `=> HasCompositionChildVisual;` in `src/Uno.UI/UI/Xaml/FrameworkElement.cs` — a **repo-wide** change making every `FrameworkElement` with a composition child visual hit-testable, shipped inside an AVP PR with no hit-test regression evidence. ### Two places the evidence genuinely conflicts, and my call

1. **`m_playDuration` in the ctor vs in `Start()`.** WinUI computes in the ctor (`cpp:22-27`, read) and I confirmed via `cpp:1055-1077` that every path WinUI actually exercises has `Duration` set first — so the ctor is right, and B's move is an unmarked simplification. But the case where it *is* wrong (PlayAsync before load) is rare on Windows and normal on Uno because of async sources. **I would take A's ctor computation with a `Start()`-time recompute guarded on `duration == 0`, marked `// TODO Uno:`.** What would settle it: a `/winui-runtime-tests` run on Windows calling `PlayAsync(0,1,false)` on a player whose `Source` is assigned one frame later, then asserting whether `IsPlaying` ever goes true. If Windows says no, the guard is a deliberate improvement and must stay marked; if yes, my reading of `cpp:708-713` is wrong and B's unconditional move is simply correct.

2. **`FrameworkElement.IsViewHit()` repo-wide vs player-scoped.** B's change is arguably more correct in general — an element hosting a composition child visual has visible content and should be hittable. But it ships an unvalidated framework-wide hit-test change inside a control PR. **I would narrow it to `AnimatedVisualPlayer` for this PR** and file the general version separately. What would settle it: run the full pointer/hit-test runtime-test namespace with B's version in place; if it is green, promote the general change in its own PR with that run as evidence.
