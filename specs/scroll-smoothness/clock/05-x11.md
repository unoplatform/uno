# Frame clock sources on Linux (X11, XWayland, DRM/KMS framebuffer)

Scope: can Uno's Skia pipeline obtain a **real** frame timestamp on Linux — either the vsync time the
frame is aligned to, or the predicted presentation time of the frame being recorded — instead of the
phase-locked estimator in `Compositor.GetFrameTimestamp`?

**Short answer: yes, and better than expected.** The epoch works out perfectly (UST and .NET
`Stopwatch` are the *same clock* on Linux, off only by a factor of 1000), Uno's own DRM/KMS
framebuffer host *already receives* a hardware vblank timestamp and throws it away, and the X11 route
via the Present extension is well-trodden. But the X11 desktop host has a bigger problem first: it is
**not vsync-paced at all** — it runs on a free-running `System.Timers.Timer`. Fixing the clock without
fixing the pacing buys much less than it looks.

---

## 1. What Uno's X11 host does today

### 1.1 Frames are paced by a .NET timer, not by the display

`src/Uno.UI.Runtime.Skia.X11/Rendering/X11XamlRootHost.Rendering.cs:15-59`

```csharp
private FramePacer CreateFramePacer()
{
    return new FramePacer(
        FeatureConfiguration.CompositionTarget.FrameRate,
        () => _renderRequested.Set());
}
...
private void RenderLoop()
{
    while (_renderLoopRunning)
    {
        _renderRequested.WaitOne();
        _framePacer.OnFrameStart();
        _renderer?.Render();
    }
}
```

`FramePacer` (`src/Uno.UI.Runtime.Skia/Hosting/FramePacer.cs:19-75`) is a `System.Timers.Timer` whose
interval is recomputed from an absolute target grid held in `Stopwatch` ticks. There is **no vsync
signal anywhere in the X11 backend**. Verified by exhaustive grep of
`src/Uno.UI.Runtime.Skia.X11/**/*.cs`: no `glXSwapIntervalEXT`, no `glXGetSyncValuesOML`, no
`glXWaitForMscOML`, no `xcb_present_*`, no `_NET_WM_SYNC_REQUEST_COUNTER` / `_NET_WM_FRAME_DRAWN`, no
`XSyncCreateCounter`. The `XSync` calls in `X11XamlRootHost.cs` are `XLib.XSync(display, false)`
(round-trip flush), not the XSync extension.

Consequences:

- The record cadence is a free-running timer. `System.Timers.Timer` → `System.Threading.Timer` →
  the .NET timer queue: millisecond granularity at best, thread-pool dispatch jitter on top.
- The timer period and the display period are **independent oscillators**. Even when the period is
  correct (see 1.2) the phase drifts, so the app beats against the display: periodic duplicated and
  skipped frames regardless of how clean the curve evaluation is.
- The Vulkan swapchain prefers `VK_PRESENT_MODE_MAILBOX_KHR`
  (`src/Uno.UI/Vulkan/Interop/VulkanDisplay.skia.cs:104-109`), which returns without waiting — so the
  Vulkan path is not vsync-blocked either. The GLX path (`X11OpenGLRenderer.Flush`,
  `src/Uno.UI.Runtime.Skia.X11/Rendering/X11OpenGLRenderer.cs:69-76`) calls `glXSwapBuffers` without
  ever setting a swap interval, so it inherits the Mesa default (interval 1 unless `vblank_mode=0`)
  — the *present* may block on vsync, but the **record** never does, which is the case that matters
  here.

### 1.2 Uno already computes the exact refresh rate and hides it from the frame clock

`src/Uno.UI.Runtime.Skia.X11/Graphics/Display/X11DisplayInformationExtension.cs:458-500` derives the
refresh rate from the XRandR mode line (`dotClock / (hTotal * vTotal)`, with interlace/doublescan
correction — a straight port of `xrandr`'s `mode_refresh`). It is delivered at line 220:

```csharp
if (fps is not null)
{
    _host.UpdateRenderTimerFps(fps.Value);
}
```

…into `FramePacer` and **nowhere else**
(`src/Uno.UI.Runtime.Skia.X11/Rendering/X11XamlRootHost.Rendering.cs:45-51`). Meanwhile
`Compositor.GetFrameTimestamp` re-derives the very same number as
`MedianFrameDelta()` over 32 jittery record intervals
(`src/Uno.UI.Composition/Composition/Compositor.skia.cs:267, 292-299`).

That is a free accuracy win with zero new platform plumbing: the estimator's *period* should come
from the mode line, not from a median of noise.

### 1.3 Where the record actually happens

`Compositor.RenderRootVisual` raises `FrameStarting`
(`src/Uno.UI.Composition/Composition/Compositor.skia.cs:308-316`) and is reached from
`CompositionTarget.Render()` → `SkiaRenderHelper.RecordPictureAndReturnPath`
(`src/Uno.UI/UI/Xaml/Media/CompositionTarget.Rendering.skia.cs:110-124`), which runs on the UI thread
via `NativeDispatcher`. On X11 the chain is:

```
FramePacer timer (thread-pool)
  → _renderRequested.Set()
  → render thread: X11Renderer.Render()
  → CompositionTarget.OnNativePlatformFrameRequested()      (render thread)
  → NativeDispatcher.Main.EnqueueRender(EnqueueRenderCallback)
  → UI thread: CompositionTarget.Render()  ← the record, FrameStarting fires here
```

`src/Uno.UI/UI/Xaml/Media/CompositionTarget.RenderScheduling.skia.cs:166-176`. So the record is **two
hops and one dispatcher queue** away from the pacing signal. Any timestamp we obtain at the pacing
signal must be published to the compositor as data, not read at record time.

### 1.4 Uno *already receives* a hardware vblank timestamp on Linux — and discards it

`src/Uno.UI.Runtime.Skia.Linux.FrameBuffer/Rendering/DRMRenderer.cs:377-393`:

```csharp
[UnmanagedCallersOnly(CallConvs = [typeof(CallConvCdecl)])]
private static unsafe void OnPageFlip(int fd, uint sequence, uint tv_sec, uint tv_usec, uint crtd_id, void* user_data)
{
    var handle = GCHandle.FromIntPtr((IntPtr)user_data);
    var @this = (DRMRenderer)handle.Target!;
    ...
    @this.Render();
```

`sequence` is the vblank counter (the MSC). `tv_sec`/`tv_usec` are the **hardware vblank timestamp**
of the flip completion, on `CLOCK_MONOTONIC` (see §3). All three parameters are unused. The frame
is recorded (via the same `Render()` → `EnqueueRender` hop) in direct response to a real vblank, and
the exact time of that vblank is sitting in the callback arguments.

This is the same shape as Android's `DoFrame(long frameTimeNanos)`
(`src/Uno.UI.Runtime.Skia.Android/Rendering/ChoreographerFramePacer.cs:99`), which also discards its
argument.

Note also `DRMRenderer.CalculateRefreshRate` (line 264) — the exact mode-line refresh rate, again
already computed.

### 1.5 There is no Wayland backend

`ls src | grep -i wayland` → nothing. On a Wayland session Uno runs the X11 backend under **XWayland**
(`X11HostBuilder.cs:60` gates on `DISPLAY`, which XWayland sets). This matters a lot for timestamp
quality — see §2.5.

## 2. The candidate sources, by category

Categories per the brief: **(a)** vsync/frame-start time, **(b)** *predicted* presentation time of the
frame being built, **(c)** *measured* presentation time reported after the fact. Only (a) and (b) can
drive a curve; (c) can only be turned into (b) by adding a refresh period.

### 2.1 GLX_OML_sync_control — category (a). Usable, with a round-trip caveat.

`glXGetSyncValuesOML(dpy, drawable, &ust, &msc, &sbc)` returns the UST/MSC/SBC triple of the most
recent vertical retrace. The spec is explicit that the UST is anchored to scanout:

> "A UST timestamp is obtained each time the graphics MSC is incremented. If this value does not
> reflect the value of the UST at the time the first scan line of the display begins passing through
> the video output port, it will be adjusted by the graphics driver to do so prior to being returned
> by any of the functions defined by this extension."
>
> — GLX_OML_sync_control spec, Khronos registry (quoted via
> `people.freedesktop.org/~marcheu/extensions/OML/glx_sync_control.html`; the registry copy at
> `registry.khronos.org` returned HTTP 403 to direct fetch)

The same spec deliberately refuses to pin the clock:

> "The Unadjusted System Time (or UST) is a 64-bit monotonically increasing counter that is available
> throughout the system. UST is not a resource that is controlled by OpenGL, so it is not defined
> further as part of this extension."

That undefined base is why Chromium disambiguates it empirically — see §3.2.

`glXWaitForMscOML(dpy, drawable, target_msc, divisor, remainder, &ust, &msc, &sbc)` blocks until the
target MSC and returns the (a) timestamp of that retrace. That is a genuine vsync-blocking wait —
i.e. it could replace the `FramePacer` timer outright on the GLX path.

**Cost caveat (Mesa/DRI3).** `glXGetSyncValuesOML` is *not* a cheap local read on Mesa. In
`src/glx/dri3_glx.c` the vtable is wired as:

```c
psp->getDrawableMSC = dri3_drawable_get_msc;
psp->waitForMSC     = dri3_wait_for_msc;

static int
dri3_drawable_get_msc(struct glx_screen *psc, __GLXDRIdrawable *pdraw,
                      int64_t *ust, int64_t *msc, int64_t *sbc)
{
   return dri3_wait_for_msc(pdraw, 0, 0, 0, ust, msc, sbc);
}
```

…which delegates to `loader_dri3_wait_for_msc` in `src/loader/loader_dri3_helper.c`, which issues
`xcb_present_notify_msc()` and then spins in `dri3_wait_for_event()` until the matching serial
arrives, finally returning `*ust = draw->notify_ust; *msc = draw->notify_msc;`. So every call is a
**synchronous X round-trip that can block**. Calling it once per frame *on the UI thread at record
time* would be a latency regression. It must be called on the render thread (which already
round-trips on swap) and published forward.

> Source read from the `notaz/mesa` GitHub mirror (`src/glx/dri3_glx.c`,
> `src/loader/loader_dri3_helper.c`). **Partially verified**: that mirror is a fork and may lag
> upstream Mesa; `gitlab.freedesktop.org` raw fetches are behind an Anubis challenge and returned an
> access-denied page. The vtable wiring and the `notify_ust`/`notify_msc` plumbing are what I read;
> I did not diff them against current upstream main.

**Availability.** Mesa exposes `GLX_OML_sync_control` for direct rendering (DRI2/DRI3); the NVIDIA
proprietary driver also exposes it. It is absent over indirect/remote GLX. Uno already has the
extension-string helper it would need: `GlxInterface.GetExtensions(display)`
(`src/Uno.UI.Runtime.Skia.X11/X11_Bindings/x11bindings_Glx.cs:139-144`) and
`glXGetProcAddress`/`SafeGetProcAddress` (lines 89-137). **UNVERIFIED** on any specific machine — I
could not run an X11 session from this Windows worktree.

### 2.2 X Present extension directly — category (a), and the better engineering choice

`xcb_present_notify_msc(conn, window, serial, target_msc, divisor, remainder)` plus
`xcb_present_select_input(..., XCB_PRESENT_EVENT_MASK_COMPLETE_NOTIFY)` and
`xcb_register_for_special_xge()` gives an **asynchronous** `PresentCompleteNotify` event carrying
`ust` and `msc`, with no blocking round-trip on the caller. Re-arm from the event handler for a
free-running per-vblank stream.

This is strictly better than 2.1 for Uno's shape, because:

- it does not block whoever calls it;
- it works for the software and Vulkan renderers too, not just GLX;
- it can live on its own `Display` connection and its own thread, which the X11 host already does
  elsewhere (`X11DisplayInformationExtension.TryGetXResource` opens a second display,
  `X11DisplayInformationExtension.cs:275`).

It is the same event Mesa itself consumes underneath `glXGetSyncValuesOML`, so the `ust` is identical
— you just skip the synchronous wrapper.

`PresentCompleteNotify` for a `PresentPixmap` you submitted is category (c) (it reports when *your*
pixmap was presented). `PresentCompleteNotify` for a `PresentNotifyMSC` request is category (a): it
reports the UST of the retrace at that MSC, independent of any of your buffers.

### 2.3 EGL — mostly not what we need

- **`EGL_ANDROID_presentation_time`** (`eglPresentationTimeANDROID`) is a **setter**, not a getter:
  you tell the compositor the earliest time you want the frame shown. It gives you no timestamp. Not
  a clock source. (Uno's X11 EGL renderer, `X11EGLRenderer.cs`, uses none of this today.)
- **`EGL_EXT_buffer_age`** returns the age in frames of the buffer you just got. It is a damage-
  tracking aid, not a clock.
- **`EGL_CHROMIUM_sync_control`** (`eglGetSyncValuesCHROMIUM`) is the EGL analogue of
  `glXGetSyncValuesOML` and returns the same UST/MSC/SBC triple. This is what Chromium's
  `SyncControlVSyncProvider` uses on the EGL path. **UNVERIFIED** whether upstream Mesa exposes it on
  the X11/EGL platform — I did not read Mesa's `src/egl` for the extension string.
- **`EGL_ANDROID_get_frame_timestamps`** is SurfaceFlinger-specific; not available on desktop Mesa.

### 2.4 Vulkan — the right long-term API, too new to depend on

- **`VK_GOOGLE_display_timing`**: `vkGetRefreshCycleDurationGOOGLE` (the true refresh period) plus
  `vkGetPastPresentationTimingGOOGLE` (category (c): `desiredPresentTime`, `actualPresentTime`,
  `earliestPresentTime`, `presentMargin`), plus `VkPresentTimeGOOGLE` on submit (a request, like
  `EGL_ANDROID_presentation_time`).
- **`VK_EXT_present_timing`**: the standardised successor.

Timeline (per Phoronix reporting, **UNVERIFIED against Mesa git**): `VK_EXT_present_timing` merged to
Mesa **26.1** for X11 and XWayland; `VK_GOOGLE_display_timing` landed in Mesa **26.2** for
`VK_KHR_display` (direct display mode). Both are bleeding-edge as of mid-2026 and cannot be a
baseline dependency. Worth revisiting once Mesa 26.x is common, since Uno already ships a Vulkan
renderer on X11.

Note also that any of this would require moving off `VK_PRESENT_MODE_MAILBOX_KHR`
(`src/Uno.UI/Vulkan/Interop/VulkanDisplay.skia.cs:104`) to FIFO for the timing to mean anything.

### 2.5 Wayland — reachable only through XWayland today, and that changes the answer

Uno has no Wayland backend, so the relevant question is: *what does the Present `ust` mean under
XWayland?* Answer: it is **not a hardware vblank**.

xorg-xserver `hw/xwayland/xwayland-present.c` (metux mirror @ `610e91dc`, 2025-06-06) sets, in both
`xwl_present_sync_callback` and `xwl_present_msc_bump`:

```c
xwl_present_window->ust = GetTimeInMicros();
```

A GitHub code search over that tree for `presentation_feedback` returns **0 hits** — XWayland at that
revision does not consume `wp_presentation_feedback` at all. So the `ust` you get on a Wayland desktop
is the moment XWayland processed the `wl_surface.frame` callback, i.e. the compositor's repaint
cadence with dispatch jitter on top. That is still **cadence-correct** (the compositor's repaint loop
is vsync-derived), and vastly better than a free-running .NET timer, but it is a software timestamp,
not scanout.

Same story for the no-hardware-vblank fallback: `present/present_fake.c` uses
`*ust = GetTimeInMicros();` and synthesises an MSC by dividing by a fake interval, with the comment:

> "For screens with hardware vblank support, the fake code will be used for off-screen windows and
> while screens are blanked, in which case we want a large interval here: 1Hz. Otherwise, pretend
> that the screen runs at 60Hz"

**Implication:** any consumer must sanity-check the `ust`/`msc` stream and be prepared to fall back —
an MSC that advances at a suspiciously round 60 Hz on a 144 Hz panel means `present_fake`, and a UST
that is not monotone-with-the-refresh means the window is not being scanned out.

For completeness, the native Wayland protocol (if a backend is ever written):
`wp_presentation_feedback.presented` is explicitly category (c) —

> "corresponds to the time when the content update turned into light the first time on the surface's
> main output"

— but it also carries `refresh`:

> "The 'refresh' argument gives the compositor's prediction of how many nanoseconds after tv_sec,
> tv_nsec the very next output refresh may occur."

So `presented(N).time + refresh` is a compositor-supplied **(b)**. And `wp_presentation.clock_id`
announces the clock domain explicitly:

> "This event tells the client in which clock domain the compositor interprets the timestamps used by
> the presentation extension. This clock is called the presentation clock."

— i.e. Wayland solves the epoch ambiguity that OML left open. `wl_surface.frame` on its own is a
"now is a good time to draw" callback with no timestamp.

> presentation-time.xml read via the `neonkore/waypipe` vendored copy — **mirror, not upstream
> `wayland-protocols`**; `raw.githubusercontent.com/wayland-project/...` 404s. Wording matches the
> stable protocol as I know it, but treat the exact revision as unverified.

### 2.6 The EWMH route: `_NET_WM_FRAME_DRAWN` / `_NET_WM_FRAME_TIMINGS` — category (c) → (b)

This is what **GTK actually uses on X11**, and Uno does not implement it. Under the extended
`_NET_WM_SYNC_REQUEST` protocol, a compositing WM (mutter, kwin) sends the client two client
messages per frame. GTK decodes them in `gdk/x11/gdkdisplay-x11.c` (GNOME/gtk `main`):

```c
guint64 serial = ((guint64)d1 << 32) | d0;
gint64 frame_drawn_time = server_time_to_monotonic_time(
  GDK_X11_DISPLAY(display), ((guint64)d3 << 32) | d2);
```

```c
gint32 presentation_time_offset = (gint32)d2;
gint32 refresh_interval = d3;

if (timings->drawn_time && presentation_time_offset) {
  gdk_frame_clock_presented(clock, frame_counter,
    (uint64_t)(timings->drawn_time + presentation_time_offset)*1000,
    refresh_interval * 1000);
}
```

So the compositor hands the client both a measured presentation time **and** the refresh interval,
already converted into the process's monotonic clock by `server_time_to_monotonic_time`.

Trade-offs vs. Present: it works for any renderer (no GL/Vulkan/DRI3 requirement) and it is the
*compositor's* view of presentation (which is what the user sees when a compositor is
redirecting the window), but it requires a cooperating EWMH compositor, requires implementing the
sync-counter handshake, and yields nothing on a bare unredirected X session.

## 3. The epoch — this is the good news

### 3.1 The verified chain

| Layer | Clock | Units | Evidence |
|---|---|---|---|
| .NET `Stopwatch.GetTimestamp()` on Linux | `clock_gettime(CLOCK_MONOTONIC)` | **nanoseconds**, `Frequency == 1_000_000_000` | dotnet/runtime `main` |
| Linux DRM vblank / page-flip events | `CLOCK_MONOTONIC` (always, since 4.15) | `tv_sec` + `tv_usec` | torvalds/linux `main` |
| X server `GetTimeInMicros()` | `clock_gettime(CLOCK_MONOTONIC)` | microseconds | xorg-xserver `os/utils.c` |
| Present UST via modesetting DDX | from DRM, above | microseconds | xorg-xserver `hw/xfree86/drivers/modesetting/vblank.c` |
| Present UST via XWayland / `present_fake` | `GetTimeInMicros()` | microseconds | xorg-xserver `xwayland-present.c`, `present_fake.c` |

**.NET.** `System.Private.CoreLib/src/System/Diagnostics/Stopwatch.Unix.cs`:

```csharp
public static long GetTimestamp() => Interop.Sys.GetTimestamp();
// GetFrequency(): const long SecondsToNanoSeconds = 1000000000; return SecondsToNanoSeconds;
```

`src/native/libs/System.Native/pal_time.c`: `SystemNative_GetTimestamp` → `minipal_hires_ticks()`.
`src/native/minipal/time.c`:

```c
int64_t minipal_hires_ticks(void)
{
#if HAVE_CLOCK_GETTIME_NSEC_NP
    return (int64_t)clock_gettime_nsec_np(CLOCK_UPTIME_RAW);
#else
    struct timespec ts;
    int result;
    result = clock_gettime(CLOCK_MONOTONIC, &ts);
    assert(result == 0 && "clock_gettime(CLOCK_MONOTONIC) failed");

    return ((int64_t)(ts.tv_sec) * (int64_t)(tccSecondsToNanoSeconds)) +
           (int64_t)(ts.tv_nsec);
#endif
}
```

`HAVE_CLOCK_GETTIME_NSEC_NP` / `CLOCK_UPTIME_RAW` is the Apple branch; glibc does not provide
`clock_gettime_nsec_np`, so **on Linux this is `CLOCK_MONOTONIC` in nanoseconds**. Note that Uno's
`Compositor.TimestampInTicks` then rescales by `s_tickFrequency = TimeSpan.TicksPerSecond /
Stopwatch.Frequency` = `10_000_000 / 1_000_000_000` = 0.01, i.e. it converts ns → 100 ns
`TimeSpan` ticks (`src/Uno.UI.Composition/Composition/Compositor.cs:31-38`, whose comment already
flags "s_tickFrequency is likely 1 on Windows, but not on Linux").

**Kernel.** `include/uapi/drm/drm.h`:

```c
/**
 * DRM_CAP_TIMESTAMP_MONOTONIC
 *
 * If set to 0, the kernel will report timestamps with ``CLOCK_REALTIME`` in
 * struct drm_event_vblank. If set to 1, the kernel will report timestamps with
 * ``CLOCK_MONOTONIC``. See ``clock_gettime(2)`` for the definition of these
 * clocks.
 *
 * Starting from kernel version 2.6.39, the default value for this capability
 * is 1. Starting kernel version 4.15, this capability is always set to 1.
 */
#define DRM_CAP_TIMESTAMP_MONOTONIC	0x6
```

**X server.** `os/utils.c` `GetTimeInMicros()` uses `clock_gettime(CLOCK_MONOTONIC)` (falling back to
`X_GETTIMEOFDAY` only where the monotonic clock is unavailable — irrelevant on Linux).
`hw/xfree86/drivers/modesetting/vblank.c`:

```c
int
ms_get_crtc_ust_msc(xf86CrtcPtr crtc, CARD64 *ust, CARD64 *msc)
{
    ...
    if (!ms_get_kernel_ust_msc(crtc, &kernel_msc, ust))
        return BadMatch;
    *msc = ms_kernel_msc_to_crtc_msc(crtc, kernel_msc, ms->has_queue_sequence);
    return Success;
}
```

with `ms_get_kernel_ust_msc` converting either `drmCrtcGetSequence`'s nanoseconds (`*ust = ns / 1000`)
or `drmWaitVBlank`'s timeval (`*ust = vbl.reply.tval_sec * 1000000 + vbl.reply.tval_usec`).

### 3.2 Conclusion, and the one guard worth keeping

> **UST (microseconds) × 1000 is directly comparable to `Stopwatch.GetTimestamp()` (nanoseconds) on
> Linux. No offset, no calibration — same clock, different scale.**

Equivalently, in Uno's `TimeSpan`-tick space: `timestampInTicks = ust * 10`.

The one caveat is that the OML spec leaves the UST base undefined, and Chromium's real-world code
proves that some drivers get it wrong. `ui/gl/sync_control_vsync_provider.cc` (chromium `main`)
carries all of these guards:

- MSC sanity: *"Both Intel and Mali drivers will return TRUE for GetSyncValues but a value of 0 for
  MSC if they cannot access the CRTC data structure"* → reject.
- Clock disambiguation: it compares the returned `system_time` against **both** `CLOCK_REALTIME` and
  `CLOCK_MONOTONIC` and picks whichever is closest without being in the future, commenting *"We need
  the time according to CLOCK_MONOTONIC, so if we've been given a time from CLOCK_REALTIME, we need
  to convert."*
- Bounds: reject if the timestamp is more than one frame in the future, or
  `monotonic_time_in_microseconds - system_time > kMicrosecondsPerSecond`.
- Interval sanity: intervals must land between 2.5 ms and 100 ms, with a 5 % relative-difference
  noise filter and a 60 fps fallback.

> Chromium file read via `raw.githubusercontent.com/chromium/chromium/main/...`. The quoted comment
> fragments are as returned by the fetch; I did **not** obtain a full verbatim listing of the file,
> so treat the surrounding control flow as paraphrase and the quoted strings as verbatim.

Recommendation: take Chromium's design as-is — accept the timestamp only if it is within one refresh
period of `Stopwatch.GetTimestamp()`, reject `msc == 0`, and fall back to the estimator otherwise. On
a healthy Linux stack the check will always pass; when it fails you genuinely do not want the value.

## 4. What the mature stacks actually feed their scroll/animation curves

### 4.1 Avalonia on X11 — nothing. A 60 Hz sleep loop.

`src/Avalonia.X11/X11Platform.cs:76-78` (Avalonia `master` @ `e81f3f7f`, 2026-04-23):

```csharp
IRenderTimer timer = options.ShouldRenderOnUIThread
   ? new UiThreadRenderTimer(60)
   : new SleepLoopRenderTimer(60);
```

`src/Avalonia.Base/Rendering/SleepLoopRenderTimer.cs:52-68`:

```csharp
void LoopProc()
{
    var lastTick = _st.Elapsed;
    while (true)
    {
        if (_stopped) _wakeEvent.WaitOne();
        var now = _st.Elapsed;
        var timeTillNextTick = lastTick + _timeBetweenTicks - now;
        if (timeTillNextTick.TotalMilliseconds > 1)
            _wakeEvent.WaitOne(timeTillNextTick);
        lastTick = now = _st.Elapsed;
        _tick?.Invoke(now);       // ← this raw Stopwatch reading is the animation clock
    }
}
```

The timestamp handed to the animation clock is the raw `Stopwatch.Elapsed` at the instant the sleep
loop happened to wake. That is *worse* than Uno's current estimator: same jitter, no smoothing, and a
hardcoded 60 Hz that ignores the actual mode line. Avalonia's X11 backend also implements the XSync
counter (`X11Window.cs:262-266, 1024-1027`) but only for `_NET_WM_SYNC_REQUEST` resize
throttling — it does **not** consume `_NET_WM_FRAME_TIMINGS`.

Avalonia's DRM/KMS backend gets the real thing and drops it, exactly like Uno:
`src/Linux/Avalonia.LinuxFramebuffer/Output/DrmOutput.cs`:

```csharp
DrmEventPageFlipHandlerDelegate flipCb =
    (int fd, uint sequence, uint tv_sec, uint tv_usec, void* user_data) =>
    {
        waitingForFlip = false;
    };
```

### 4.2 Flutter on Linux (GTK embedder) — a *snapped grid*, not the raw clock

The GTK embedder never installs `FlutterProjectArgs.vsync_callback` (grep of

### 4.3 GTK4 — has a real presentation time on X11 *and* still smooths it

This is the most instructive precedent, because GTK4 is the one stack here that genuinely obtains a
compositor-reported presentation time on X11 (§2.6) and on Wayland (`wp_presentation`), and it
**still** runs a phase-locked estimator over it before handing a time to animations.

`gdk/gdkframeclockidle.c` (GNOME/gtk `main`):

```c
/* Note: This is never called on first frame, so
 * smoothed_frame_time_base != 0 and we have a valid frame_interval. */
static uint64_t
compute_smooth_frame_time (GdkFrameClockIdle *self,
                           uint64_t           new_frame_time,
                           gboolean           new_frame_time_is_vsync_related,
                           uint64_t           smoothed_frame_time_base,
                           uint64_t           frame_interval)
{
  ...
  /* Consecutive frame, assume it is an integer number of frames later, so round to nearest such */
  if (new_frame_time < smoothed_frame_time_base + frame_interval / 2)
    frames_passed = 0;
  else
    frames_passed = (new_frame_time - smoothed_frame_time_base + frame_interval / 2) / frame_interval;

  /* We use an approximately whole number of frames in the future from
   * last smoothed frame time. This way we avoid minor jitter in the
   * frame times making the animation speed uneven, but still animate
   * evenly in case of whole frame skips. */
  new_smoothed_time = smoothed_frame_time_base + frames_passed * frame_interval;

  /* However, sometimes the smoothed time is too much off from the
   * real time. For example, if the first frame clock cycle happened
   * not due to a frame rendering but an input event, then
   * new_frame_time could happen to be near the middle between two
   * frames. If that happens and we then start regularly animating at
   * the refresh_rate, then the jitter in the real time may cause us
   * to randomly sometimes round up, and sometimes down.
   *
   * To combat this we converge the smooth time towards the real time
   * in a way that is slow when they are near and fast when they are
   * far from each other.
   *
   * This is done by using the square of the error as the correction
   * magnitude. I.e. if the error is 0.5 frame, we correct by
   * 0.5*0.5=0.25 frame, if the error is 0.25 we correct by 0.125, if
   * the error is 0.1, frame we correct by 0.01 frame, etc.
   *
   * The actual computation is:
   *   (current_error/frame_interval)*(current_error/frame_interval)*frame_interval
   * But this can be simplified as below.
   *
   * Note: We only do this correction if the new frame is caused by a
   * thaw of the frame clock, so that we know the time is actually
   * related to the physical vblank. For frameclock cycles triggered
   * by other events we always step up in whole frames from the last
   * reported time.
   */
  if (new_frame_time_is_vsync_related)
    {
      current_error = MAX (new_smoothed_time, new_frame_time) - MIN (new_smoothed_time, new_frame_time);
      correction_magnitude = current_error * current_error / frame_interval;
      if (new_smoothed_time > new_frame_time)
        new_smoothed_time -= correction_magnitude;
      else
        new_smoothed_time += correction_magnitude;
    }

  /* Ensure we're always monotonic  */
  if (new_smoothed_time <= priv->smoothed_frame_time_reported)
    new_smoothed_time = priv->smoothed_frame_time_reported;

  return new_smoothed_time;
}
```

Four differences worth importing into `Compositor.GetFrameTimestamp`
(`src/Uno.UI.Composition/Composition/Compositor.skia.cs:244-290`):

1. **Quadratic correction.** GTK corrects by `error² / interval`; Uno corrects by `error / 16`
   (line 286). GTK's law is self-damping: fast convergence when far off, near-zero pull when close,
   with no magic constant. Uno's linear `/16` has a fixed time constant regardless of error size, so
   it is simultaneously too slow to recover from a bad initial phase and too eager near lock.
2. **Whole-frame rounding for *every* gap.** GTK always computes `frames_passed` by rounding, then
   corrects; Uno only slips by whole periods when `|error| >= period` (line 276) and otherwise
   assumes exactly one frame passed. Behaviourally close, but GTK's formulation has no
   discontinuity at the one-period boundary.
3. **Monotonicity clamp.** GTK explicitly clamps `new_smoothed_time` to never go backwards. Uno has
   no such clamp; with `_frameClock += period + error/16` it is monotone only while
   `|error/16| < period`, which holds today but is an unstated invariant.
4. **Provenance flag — the real gap.** GTK smooths against the real clock *only* when the wakeup was
   `new_frame_time_is_vsync_related`; for cycles triggered by input or other events it steps in whole
   frames from the last reported time. Uno has no such distinction: any off-cadence record — an input
   event, a layout invalidation, `RequestFrame` from a newly-subscribed driver
   (`Compositor.skia.cs:217`) — feeds `GetFrameTimestamp` and drags the grid's phase. **This is a
   real defect in the current estimator, independent of whether we ever get a hardware timestamp.**

### 4.4 Chromium

Uses `glXGetSyncValuesOML` / `eglGetSyncValuesCHROMIUM` through `SyncControlVSyncProvider` to derive
a (timebase, interval) pair, and drives compositing off that — i.e. it *does* take the real (a)
timestamp on X11, with the extensive validation described in §3.2.

## 5. Recommendation

Staged, cheapest-first. Each stage is independently shippable.

**Stage 0 — feed the estimator the real period (trivial, X11 + framebuffer).**
Uno already knows the exact refresh rate from the XRandR mode line
(`X11DisplayInformationExtension.cs:492-500`) and from the DRM mode line
(`DRMRenderer.CalculateRefreshRate`, `DRMRenderer.cs:264`). Route it into the compositor as the
frame period instead of `MedianFrameDelta()` (`Compositor.skia.cs:267`). Removes an entire estimator
stage and the 8-sample warm-up. No new platform API.

**Stage 1 — adopt GTK's estimator refinements (trivial, all platforms).**
Quadratic `error²/period` correction, monotonicity clamp, and — most importantly — a
`isCadenceRelated` flag on the record so that off-cadence records (input, layout, first frame after
subscribe) step in whole frames instead of dragging the phase. §4.3 items 1–4. This is worth doing
*whether or not* any hardware timestamp ever arrives.

**Stage 2 — use the vblank timestamp Uno already has (small, framebuffer host).**
`DRMRenderer.OnPageFlip` (`DRMRenderer.cs:378`) receives `sequence`, `tv_sec`, `tv_usec`. Publish
`(tv_sec * 1_000_000L + tv_usec) * 10` — TimeSpan ticks, same epoch as
`Compositor.TimestampInTicks` — into a volatile field the compositor reads at record time, together
with `sequence` so dropped frames are detectable exactly rather than inferred. This is a genuine
category-(a) hardware vsync time and it costs nothing to obtain. Lowest-risk place to *validate the
whole idea* on Linux.

**Stage 3 — X Present event stream (medium, X11 host).**
A dedicated `Display` connection + `xcb_present_select_input` +
`xcb_present_notify_msc(divisor=1)`, re-armed from the handler, on its own thread. Publishes
`(ust, msc)` the same way as Stage 2. Prefer this over `glXGetSyncValuesOML` (§2.2): non-blocking,
renderer-agnostic, same underlying `ust`. Gate every value with the Chromium guards (§3.2), and
detect `present_fake`/XWayland by checking whether the MSC rate matches the XRandR mode line.

Additionally, once the MSC stream exists, `glXWaitForMscOML` or a Present-event wait can **replace
the `System.Timers.Timer` in `FramePacer`** on X11 — which addresses the free-running-oscillator
problem in §1.1 that the clock work alone does not.

**Not recommended now:** `VK_EXT_present_timing` / `VK_GOOGLE_display_timing` (Mesa 26.1/26.2, too
new); `_NET_WM_FRAME_TIMINGS` (needs a cooperating compositor and a sync-counter handshake Uno does
not have, and yields nothing unredirected); a native Wayland backend (out of scope, but note it would
be the only path to a *compositor-declared* clock domain via `wp_presentation.clock_id`).

**Honest caveat.** On a Wayland desktop — which is the default on current GNOME and KDE — Stage 3
gives you XWayland's `GetTimeInMicros()` at frame-callback dispatch (§2.5), not scanout. Still a real
cadence, still worth having, but do not expect hardware-vblank precision there, and keep the estimator
as the fallback rather than replacing it.
