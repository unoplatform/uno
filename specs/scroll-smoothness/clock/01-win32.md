# Win32 frame clock: can we get the real vsync time?

**Scope:** Windows desktop / `Uno.UI.Runtime.Skia.Win32`. Question: can the per-frame motion drivers
(`Compositor.FrameStarting`) be handed a *real* vsync/presentation timestamp instead of the
phase-locked reconstruction in `Compositor.GetFrameTimestamp`?

**Answer: yes, and Uno is already making the call that makes it available — it just throws the result
away.** `Win32RenderPacer` blocks on `DwmFlush()` every frame. A single
`DwmGetCompositionTimingInfo(NULL, …)` immediately after that call returns `qpcVBlank`, a real VSync-ISR
timestamp on the QueryPerformanceCounter timeline. **`Stopwatch.GetTimestamp()` on Windows *is*
`QueryPerformanceCounter`** — verified empirically below, bit-for-bit — so the value needs **no epoch
conversion at all**.

Measured on this machine (Windows 11 Pro 10.0.29595, 120 Hz display, QPF = 10 MHz), against a
least-squares-fitted ideal grid over 400 frames:

| Timestamp source | jitter (rms) | peak \|residual\| |
|---|---|---|
| Record instant — *what Uno feeds drivers today* | **0.9009 ms** | 2.8990 ms |
| `DwmFlush()` return instant | 0.1637 ms | 1.8468 ms |
| **`qpcVBlank` sampled right after `DwmFlush()`** | **0.0178 ms** | **0.0467 ms** |

At the measured fling launch velocity (~2650 dip/s) that is the difference between **±2.4 dip** of
per-frame position error and **±0.05 dip**. A ~50× improvement, for one P/Invoke per frame costing a
median of 5.3 µs on a thread that is about to block for 8.3 ms anyway.

## 1. What Uno already has in hand and discards

The render thread is `Win32WindowWrapper.RenderThread` — `src/Uno.UI.Runtime.Skia.Win32/Rendering/Win32WindowWrapper.RenderThread.cs:52-90`:

```
_frameSignal.WaitOne()
StartPaint()
DrawFrame()          → OnNativePlatformFrameRequested → EnqueueRender(EnqueueRenderCallback) to the UI thread
                     → Draw() replays the previously recorded SKPicture into the surface
CopyPixels(w, h)     → BitBlt / SwapBuffers / vkQueuePresent
                     → _pacer.WaitForNextFrame()  ← DwmFlush(): blocks to the compositor
EndPaint()
```

`Win32RenderPacer.WaitForNextFrame()` — `src/Uno.UI.Runtime.Skia.Win32/Rendering/Win32RenderPacer.cs:53-89`:

```csharp
var dwmFlushResult = PInvoke.DwmFlush();   // line 61
if (dwmFlushResult.Failed) { … } else { _consecutiveDwmFlushFailures = 0; }   // line 80
```

**Line 61 is the exact instant at which DWM's timing record is fresh, and the only thing kept from it
is `HRESULT.Failed`.** Everything the frame clock needs is one call away at that point.

The record side then reads a raw wall clock: `Compositor.RenderRootVisual` →
`GetFrameTimestamp(TimestampInTicks)` (`src/Uno.UI.Composition/Composition/Compositor.skia.cs:312`),
with `TimestampInTicks => (long)(Stopwatch.GetTimestamp() * s_tickFrequency)`
(`src/Uno.UI.Composition/Composition/Compositor.cs:38`). The estimator lives at
`Compositor.skia.cs:244-299`, and `FrameIntervalInTicks` (`Compositor.skia.cs:220-222`) reconstructs the
refresh period as the median of the last 32 record deltas — a quantity DWM states exactly as
`qpcRefreshPeriod`.

Uno's `DwmFlush` P/Invoke is already generated: `src/Uno.UI.Runtime.Skia.Win32.Support/NativeMethods.txt:180`.
`DwmGetCompositionTimingInfo` is **not** in that list (checked lines 174-180: only
`DwmSetWindowAttribute`, `DwmIsCompositionEnabled`, `DwmExtendFrameIntoClientArea`, `DwmDefWindowProc`,
`DwmFlush`) — adding it is a one-line change to a CsWin32 input file.

Per-renderer availability of the `DwmFlush` hook:

| Renderer | Present | Paced by | `DwmFlush` on the follow-refresh path? |
|---|---|---|---|
| Software (`Rendering.Software.cs:26-28, 98-102`) | `BitBlt` | `Win32RenderPacer` | **Yes** |
| Vulkan (`Rendering.Vulkan.cs:27-29, 112-134`) | MAILBOX present | `Win32RenderPacer` | **Yes** |
| OpenGL (`Rendering.OpenGl.cs:118-121, 146-148, 225-241`) | `SwapBuffers` w/ `wglSwapIntervalEXT(1)` | the driver's swap-interval block; `_pacer` is **null** | **No** — see §7 |

(Vulkan if requested, else OpenGL, else Software).

## 2. The epoch question, settled by measurement

**`Stopwatch.GetTimestamp()` on Windows is literally `QueryPerformanceCounter`, and
`Stopwatch.Frequency` is literally `QueryPerformanceFrequency`.**

Empirical (`scratchpad/dwmclock.cs`, first revision — 2000 interleaved samples of
`QPC(a) / Stopwatch.GetTimestamp(s) / QPC(b)`):

```
QueryPerformanceFrequency = 10000000
Stopwatch.Frequency       = 10000000
Stopwatch.IsHighResolution= True
Interleaved QPC/Stopwatch: max out-of-bracket skew = 0 ticks (0.000000 ms)
```

Every `Stopwatch.GetTimestamp()` reading fell inside the bracket `[a, b]` of the QPC readings taken
immediately before and after it, across 2000 trials — the two are the same counter, not merely
correlated. This matches the existing note in `Compositor.cs:32-37` (which cites
`dotnet/runtime` `Stopwatch.cs` and already says "`s_tickFrequency` is likely 1 on Windows").
`s_tickFrequency = TimeSpan.TicksPerSecond / Stopwatch.Frequency = 10 000 000 / 10 000 000 = 1.0`
exactly here, so `Compositor.TimestampInTicks == QPC` **with no scaling on Windows**.

Consequences:

* `DWM_TIMING_INFO.qpcVBlank` / `qpcCompose` / `qpcRefreshPeriod` are **directly comparable to
  `Compositor.TimestampInTicks`**. No offset, no drift correction, no calibration handshake.
* Still route the value through `* s_tickFrequency` rather than hard-coding the identity — QPF is
  10 MHz by OS convention on Windows 8+, but the multiply is free and keeps the code honest.
* `Stopwatch.Frequency == QueryPerformanceFrequency` is a *documented* .NET behaviour on Windows
  (`Stopwatch` is a thin wrapper over QPC/QPF); the empirical check above is the verification.

**Verification label: Runtime (measured on this machine).** Not read from `dotnet/runtime` source —
no local clone — but the interleave test is a stronger check than reading the source would be.

## 3. `DWM_TIMING_INFO`: which fields are actually usable

Header: `C:\Program Files (x86)\Windows Kits\10\Include\10.0.26100.0\um\dwmapi.h:159-339`.
API: `DwmGetCompositionTimingInfo(HWND hwnd, DWM_TIMING_INFO* pTimingInfo)` — same header, line 426.

### 3a. The four fields that matter

| Field | Header line | Category | Verdict |
|---|---|---|---|
| `qpcVBlank` | 184 (*"QPC time at a VSync interupt"*) | **(a) vsync time** — and, sampled right after `DwmFlush`, it is the *upcoming* vblank (§4) | **Use this.** |
| `qpcRefreshPeriod` | 178 (*"Actual period"*) | exact period in QPC ticks | **Use this** — replaces `FrameIntervalInTicks`' median-of-32 estimate. Measured `83335` ticks = 8.3335 ms = 119.998 Hz, vs `rateRefresh` = 10000000/83416 (a *ratio*, and the naive integer truncation of it is 119, not 120). |
| `cRefresh` | 189 (*"DWM refresh count of the last vsync"*) | monotone vsync **index** | **Use this as the freshness/drop check.** Measured: advanced by exactly 1 on all 399 consecutive `DwmFlush` iterations (0 repeats, 0 skips). |
| `qpcCompose` | 202 (*"QPC time at a compose time"*) | (a)-ish, the composition pass time | Redundant — measured identical to `qpcVBlank` on a cold call. |

### 3b. `cfaPresented` does not exist

There is **no** `cfaPresented` field in `DWM_TIMING_INFO`. The nearest names are `cFrameConfirmed`
(line 221), `cRefreshConfirmed` (228), `cRefreshNextPresented` (299) and `cRefreshesPresented` (309).
All of them are **category (c), measured after the fact**, and all of them are **useless to Uno**:
they describe *DX presents made by the calling process through DWM's legacy present path*. Measured on
a process that does not do a DX present (which is exactly Uno's software/GL/Vulkan situation from
DWM's point of view), every one of them reads **0**, alongside `qpcFrameDisplayed = 0`,
`qpcFrameComplete = 0`, `qpcFramePending = 0`. See §8 for the full dump.

So: **`qpcVBlank` + `qpcRefreshPeriod` + `cRefresh` is the entire usable payload.** That is enough.

### 3c. Two traps that will cost you an afternoon each

**Trap 1 — `cbSize` must be 292, not `Marshal.SizeOf` of a naturally-aligned struct.**
`dwmapi.h` line 24 is `#include <pshpack1.h>` — **the whole header is `#pragma pack(1)`**. The C
`sizeof(DWM_TIMING_INFO)` is therefore **292**, while a `[StructLayout(LayoutKind.Sequential)]` C#
mirror measures **320**. Passing 320 fails with `0x88980090` = `MILERR_MISMATCHED_SIZE`
(`winerror.h:61065`). Brute-forcing every `cbSize` from 8 to 512 confirmed **292 is the only accepted
value**. The C# struct must be `[StructLayout(LayoutKind.Sequential, Pack = 1)]`.
*(CsWin32 sources its layout from win32metadata, which does model the packing — but verify the
generated struct's size is 292 before trusting it.)*

**Trap 2 — `hwnd` must be `NULL`.** The same brute-force sweep, repeated with `GetDesktopWindow()`
and `GetShellWindow()`, produced **zero** accepted `cbSize` values for either. Only
`DwmGetCompositionTimingInfo(NULL, …)` succeeds. WPF's milcore does exactly this
(`D:\Work\wpf` @ `5599cc9`, `src/Microsoft.DotNet.Wpf/src/WpfGfx/core/uce/rendertargetmanager.cpp:1202`:
`m_pfnDwmGetCompositionTimingInfo(NULL, &info)`), as does Flutter
(`D:\Work\flutter`, `engine/src/flutter/shell/platform/windows/flutter_windows_engine.cc:688`).

`NULL` means **the primary monitor**. On a mixed-refresh multi-monitor setup, a window on a secondary
monitor gets the *primary's* vblank. Mitigation in §9.

## 4. Freshness: `qpcVBlank` is only valid right after `DwmFlush`

This is the single most important operational constraint, and it is why the value has to be sampled on
the render thread rather than polled from the UI thread at record time.

**Free-running poll (no `DwmFlush`), 20 000 samples at 0.2 ms over ~4000 ms** — during which ~480
refreshes occurred:

```
FREE POLL (now - qpcVBlank) ms: min -8.257, p05 -4.970, p50 7.594, p95 26.924, max 71.816
distinct qpcVBlank values over 20000 polls spanning ~4000 ms: 224 (expect ~480)
```

DWM only refreshes its timing record for a process that is participating in composition. Polled cold,
`qpcVBlank` went **up to 71.8 ms stale** and updated fewer than half the times it should have. A
UI-thread `DwmGetCompositionTimingInfo` at record time would be *worse* than the current estimator.

**Inside a `DwmFlush` loop, 300 iterations:**

```
FLUSH LOOP (flushReturn - qpcVBlank) ms: min -7.977, p05 -7.853, p50 -7.785, p95 -7.581, max -6.823
  => DwmFlush returns 7.785 ms BEFORE the reported qpcVBlank (0.934 periods)
```

Rock-steady: a ±0.14 ms spread between p05 and p95. And note the **sign** — sampled immediately after
`DwmFlush()` returns, `qpcVBlank` is **~0.93 refresh periods in the future**. `DwmFlush` returns just
after a vblank, and DWM has already stamped the *next* one. So the value is category (a) *vsync time*
that doubles as a near-perfect category (b) *predicted present time* for the buffer that was just
BitBlt'd — no extrapolation needed to get a forward-looking timestamp.

`qpcVBlank` is a genuinely measured ISR time, not a synthesised grid: consecutive deltas were an exact
integer multiple of `qpcRefreshPeriod` only 7 times out of 399, with a **max residual of 49 ticks
(4.9 µs)**. That residual *is* the entire remaining error budget.

Cost of the call inside the loop: **median 5.30 µs, max 1181 µs** (the max is a one-off scheduling
hiccup / first-call resolve; the median is what matters, on a thread that then blocks for 8.3 ms).

## 5. `IDXGIOutput::WaitForVBlank` and `IDXGISwapChain::GetFrameStatistics`

**`IDXGIOutput::WaitForVBlank()` — not useful here.** It returns `HRESULT` and nothing else: **no
timestamp**. Using it would give you a *wake instant*, i.e. exactly the class of measurement the
`DwmFlush` return instant already provides (0.164 ms rms — 9× worse than `qpcVBlank`), plus a second
blocking sync per frame on top of the one Uno already has. This is what Avalonia does
(`D:\Work\Avalonia` @ `e81f3f7`, `src/Windows/Avalonia.Win32/DirectX/DxgiConnection.cs:102-128`): a
dedicated thread loops `_output.WaitForVBlank()` and then ticks with `_stopwatch.Elapsed` — the wall
clock at wake-up, **not** a vsync timestamp. It also falls back to `DwmFlush()` (line 120) when it
can't pick an output. Verified by reading the source.

**`IDXGISwapChain::GetFrameStatistics` (`SyncQPCTime`) — right timeline, wrong category, wrong
plumbing.**
* `DXGI_FRAME_STATISTICS.SyncQPCTime` is on the QPC timeline (so §2 applies) but it is **category (c),
  measured after the fact**: the time of the vsync at which a *previously submitted* present became
  visible. Driving a curve from it means always running one-or-more frames stale, or reconstructing a
  grid from it — which is the estimator problem again, just with a better anchor.
* It requires a **DXGI swap chain**. Uno's Win32 renderers are GDI `BitBlt`, WGL `SwapBuffers`, and
  Vulkan `vkQueuePresentKHR` — **there is no DXGI swap chain anywhere in
  `src/Uno.UI.Runtime.Skia.Win32/`**. Getting `GetFrameStatistics` means introducing a D3D/DXGI
  presentation path, which is an enormous change relative to one P/Invoke.
* It also only works reliably on flip-model swap chains in full-screen or `FLIP_DISCARD`; on windowed
  bitblt-model chains it commonly returns `DXGI_ERROR_FRAME_STATISTICS_DISJOINT` or stale counts.
  **UNVERIFIED** — stated from API knowledge, not measured here, because there is no swap chain to
  measure against.

**Verdict: skip both.** `DwmGetCompositionTimingInfo` after the `DwmFlush` Uno already performs
dominates them on accuracy, cost, and blast radius.

## 6. What the mature stacks actually feed their curves

### WPF — verified from source (`D:\Work\wpf` @ `5599cc923d6a464ea0afc7864e722a7b57ab4281`)

WPF does **exactly** the thing this document proposes, and has since v1.

Composition thread (milcore), `src/Microsoft.DotNet.Wpf/src/WpfGfx/core/uce/rendertargetmanager.cpp:1157-1218`
(`CRenderTargetManager::WaitForDwm`):

```cpp
if (!m_fQPCSupported || qpcCurrentTime < *pqpcPresentationTime) {
    MIL_THR(m_pfnDwmpFlush());                       // private DwmFlush
}
DWM_TIMING_INFO info = {0};
info.cbSize = sizeof(DWM_TIMING_INFO);
hr = m_pfnDwmGetCompositionTimingInfo(NULL, &info);  // line 1202
…
*pePresentationResults = MilPresentationResults::Dwm;
*puiRefreshRate        = info.rateCompose.uiNumerator / info.rateCompose.uiDenominator;
*pqpcPresentationTime  = info.qpcVBlank;             // line 1214
```

**Flush, then read `qpcVBlank`, and call it the presentation time.** That value is packed into a
`PresentationTime` message (`composition.cpp:2383-2405`) and sent to the UI thread.

UI thread, `src/Microsoft.DotNet.Wpf/src/PresentationCore/System/Windows/Media/MediaContext.cs`:

* `NotifyPresent` stores it: `_lastPresentationTime = presentationTime;` (lines 746 and 791, for the
  `MIL_PRESENTATION_VSYNC` and `MIL_PRESENTATION_DWM` cases).
* `IClock.CurrentTime` (lines ~1085-1182) — **this is the clock every WPF animation is ticked
  against** — extrapolates forward from it:
  ```csharp
  nextVsyncTicks        = countsTicks + TicksUntilNextVsync(countsTicks);
  nextPresentationTicks = nextVsyncTicks + vsyncAdvance * RefreshPeriod;   // vsyncAdvance = 1 while waiting on the compositor
  if ((nextPresentationTicks - _estimatedNextPresentationTime.Ticks) * _animationRenderRate
        > TimeSpan.FromMilliseconds(500).Ticks)
  {
      _estimatedNextPresentationTime = TimeSpan.FromTicks(nextPresentationTicks);   // line 1168
  }
  return _estimatedNextPresentationTime;
  ```
  with `TicksSinceLastVsync(t) = (t - CountsToTicks(_lastPresentationTime)) % RefreshPeriod`
  (lines 921-944).
* `TimeManager` is constructed with that `IClock` (`Animation/TimeManager.cs:56`), sets
  `_globalTime = GetCurrentGlobalTime()` per tick (line 360), and `CompositionTarget.Rendering` is
  raised with it: `Rendering?.Invoke(this.Dispatcher, new RenderingEventArgs(_timeManager.LastTickTime))`
  (`MediaContext.cs:1819`).

So WPF's answer to the exact question in this spec: **drivers get a predicted next-presentation time,
anchored on the real DWM `qpcVBlank`, with a half-frame hysteresis** (the "keep the previous estimate
if the new one is within half a frame" comment at `MediaContext.cs:1064-1078`) to avoid re-ticking
animations and re-running layout for sub-frame noise. Uno's `error / 16` pull
(`Compositor.skia.cs:286`) is the same idea — WPF just anchors it to a real vblank instead of
reconstructing one.

**One WPF detail worth *not* copying:** the managed side throws away `qpcRefreshPeriod` and recomputes
`RefreshPeriod = TimeSpan.TicksPerSecond / _animationRenderRate` from the **integer** rate
(`MediaContext.cs:905-911`), where the integer comes from
`rateCompose.uiNumerator / uiDenominator` in C++ (truncating 119.998 Hz to **119**). Uno should carry
`qpcRefreshPeriod` through verbatim.

### Flutter (Windows) — verified from source (`D:\Work\flutter`)

Flutter uses DWM only for the **interval**, then synthesises the grid — the same class of solution as
Uno's current estimator. `engine/src/flutter/shell/platform/windows/flutter_windows_engine.cc:670-696`:

```cpp
void FlutterWindowsEngine::OnVsync(intptr_t baton) {
  auto current_time = std::chrono::nanoseconds(embedder_api_.GetCurrentTime());
  auto frame_interval = FrameInterval();
  auto next = SnapToNextTick(current_time, start_time_, frame_interval);
  embedder_api_.OnVsync(engine_, baton, next.count(), (next + frame_interval).count());
}
// FrameInterval(): DwmGetCompositionTimingInfo(NULL, &timing_info) → rateRefresh only.
```

`SnapToNextTick` (lines 43-51) snaps to a grid whose **phase is `start_time_`, the engine start
instant** — an arbitrary constant with no relationship to the display. Flutter hands the engine both a
frame start time and a target present time (`next + interval`), i.e. it *does* drive its curves from a
predicted presentation time — it just derives it worse than WPF does. **Uno's current estimator is
already better than Flutter's Windows implementation** (it phase-locks to the observed record cadence
rather than to a fixed anchor); it is still worse than reading `qpcVBlank`.

### Avalonia — verified from source (`D:\Work\Avalonia` @ `e81f3f7`)

## 7. Concretely, what to change in Uno

### 7a. Sample it (render thread)

Add to `src/Uno.UI.Runtime.Skia.Win32.Support/NativeMethods.txt` (alongside `DwmFlush` at line 180):

```
DwmGetCompositionTimingInfo
DWM_TIMING_INFO
```

then, in `Win32RenderPacer.WaitForNextFrame()` immediately after the success branch at
`Win32RenderPacer.cs:78-81`:

```csharp
// DWM's timing record is only fresh for a process that just synchronised with it; sampling
// anywhere else returns a value up to tens of ms stale.
var info = new DWM_TIMING_INFO { cbSize = (uint)sizeof(DWM_TIMING_INFO) };   // must be 292
if (PInvoke.DwmGetCompositionTimingInfo(HWND.Null, &info).Succeeded && info.cRefresh != _lastRefreshIndex)
{
    _lastRefreshIndex = info.cRefresh;
    LatestVBlank = (long)info.qpcVBlank;          // QPC == Stopwatch.GetTimestamp()
    RefreshPeriodInQpc = (long)info.qpcRefreshPeriod;
}
```

**Assert 292 in a unit test.** If CsWin32 emits a naturally-aligned 320-byte struct, the call fails
with `MILERR_MISMATCHED_SIZE` and the whole feature silently degrades to the estimator.

### 7b. Hand it to the record (deterministically)

Do **not** let the UI thread read a shared "latest" field at record time — the render thread's next
`DwmFlush` can land in between, and which value you get becomes a race. Capture it on the render
thread at the top of the iteration, before `DrawFrame()` triggers
`NativeDispatcher.Main.EnqueueRender(…)` (`CompositionTarget.RenderScheduling.skia.cs:170-173`), and
pass it down that path so the record consumes the value that was current when the record was
*requested*.

Then in `Compositor.RenderRootVisual` (`Compositor.skia.cs:308-313`):

```csharp
var frameTimestamp = platformVBlank is { } v
    ? unchecked((long)(v * s_tickFrequency))   // == v on Windows; keep the multiply for other hosts
    : GetFrameTimestamp(TimestampInTicks);     // existing estimator, unchanged, as the fallback
```

and let `FrameIntervalInTicks` (`Compositor.skia.cs:220-222`) prefer the platform's
`qpcRefreshPeriod` over the median-of-32.

**Keep the estimator.** It is the fallback for: `_dwmFlushDegraded` (`Win32RenderPacer.cs:69`), the
fixed-`FrameRate` timer path (`SetFrameRateAsScreenRefreshRate = false`), the OpenGL renderer until
§7c is done, and every non-Win32 host.

### 7c. Phase, latency, and the drag→fling handoff — read this before adding lead

The tempting next step is "we know the present is 2 vblanks out, so evaluate the curve at
`qpcVBlank + 2 * qpcRefreshPeriod`". **Do not do that as part of this change.**

For *smoothness*, only the **uniformity** of the grid matters — a fling's `elapsed` is
`timestamp - _flingStartTimestamp` (`ScrollContentPresenter.Managed.cs:628`), and
`_flingStartTimestamp` is itself anchored on the first frame's timestamp
(`ScrollContentPresenter.Managed.cs:621-625`), so **any constant offset cancels exactly**. Switching
from the wobbling record instant to the `qpcVBlank` grid is therefore a pure jitter fix with zero
behavioural risk.

Adding forward lead is a *latency* change, and it is not free: the drag path latches finger geometry
and reads no clock at all, so leading only the inertial curve would put a 2-frame position step at the
finger-lift handoff — precisely the "user fighting" / snap failure mode this workstream is trying to
eliminate. Land the grid first, measure, and treat lead as a separate experiment with its own
before/after capture.

### 7d. The OpenGL gap

`GlRenderer` on the follow-refresh path has `_pacer == null` (`Rendering.OpenGl.cs:146-148`) — it
blocks inside `SwapBuffers` via `wglSwapIntervalEXT(1)` and never calls `DwmFlush`. Whether
`DwmGetCompositionTimingInfo` is fresh immediately after a composited `SwapBuffers` is **UNVERIFIED**
(it would need a real GL window to test; the console probe here can't reach it).

The `cRefresh` check in §7a is the answer either way: sample after `SwapBuffers`, and if `cRefresh`
did not advance since the previous frame, treat the sample as stale and fall through to the estimator
for that frame. That makes the GL path self-diagnosing rather than blocking the change — and the
telemetry (how often `cRefresh` advances) answers the UNVERIFIED question in the field.

## 9. Risks and mitigations

| Risk | Mitigation |
|---|---|
| `cbSize` mismatch → silent fallback to the estimator forever | Unit-test `sizeof(DWM_TIMING_INFO) == 292`; log once at `Warn` on the first `MILERR_MISMATCHED_SIZE`. |
| `hwnd = NULL` reports the **primary** monitor; a window on a 60 Hz secondary while the primary is 120 Hz gets the wrong grid | Cross-check `qpcRefreshPeriod` against the window's own `_refreshRate` (`Win32WindowWrapper.DisplayInformation.cs:117`, from `DEVMODEW.dmDisplayFrequency` via `EnumDisplaySettingsEx`). On disagreement beyond ~2%, fall back to the estimator for that window and log once. |
| Stale sample (DWM paused, RDP, fast user switch, GL path) | The `cRefresh != _lastRefreshIndex` guard in §7a. No advance ⇒ don't use the sample. |
| `DwmFlush` degraded path (`Win32RenderPacer.cs:67-75`) | Already permanent-degrades to the timer; simply stop publishing vblanks and the estimator takes over. |
| Race between the render thread's publish and the UI thread's read | Capture on the render thread and pass through the `EnqueueRender` path (§7b) rather than reading a shared latest-value field. |
| Variable-refresh-rate displays (G-Sync/FreeSync/Windows Dynamic Refresh Rate) | `qpcRefreshPeriod` is *"Actual period"*, re-read every frame, so a changing period is tracked automatically — strictly better than a median-of-32. Behaviour under an actively varying rate is **UNVERIFIED** (this machine is fixed 120 Hz). The `cRefresh` guard bounds the damage. |

## 10. Bottom line

* **Available:** a real vsync timestamp, `DWM_TIMING_INFO.qpcVBlank`, category (a) — and sampled where
  Uno already blocks, it sits ~0.93 refresh periods in the future, so it doubles as a category (b)
  predicted present time for the frame being pushed out.
* **Epoch:** QueryPerformanceCounter. `Stopwatch.GetTimestamp()` **is** QPC on Windows (measured: zero
  skew over 2000 interleaved samples, `Stopwatch.Frequency == QPF == 10 MHz`, so
  `s_tickFrequency == 1.0`). **No conversion, no calibration.**
* **Already in Uno, discarded:** `Win32RenderPacer.cs:61` calls `PInvoke.DwmFlush()` and keeps only the
  `HRESULT`.
* **Cost:** one CsWin32 line, one P/Invoke per frame (median 5.3 µs), plus threading the value from the
  render thread into the record. The estimator stays as the fallback.
* **Payoff:** frame-clock jitter from **0.90 ms rms** to **0.018 ms rms** — 50×, and it gets
  *relatively better* at higher refresh rates, which is exactly where the current problem worsens.
